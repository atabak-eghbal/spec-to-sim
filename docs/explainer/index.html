Spec-to-Sim

You type a robot task in plain English. A chain of NVIDIA Nemotron models turns it into a MuJoCo simulation, runs it, watches the video, and repairs the plan until the task succeeds. This page explains how it works, what has been built, and why each decision was made.

How it works

Six steps, and only the first three always run

Each step has one job and hands a validated data structure to the next. The models only ever produce data (JSON checked against a schema). Our own code builds the scene, moves the robot, and decides pass or fail.

Step 1

Planner Super

Reads the English task. Lists the objects, writes the success goals, and proposes web searches.

→ TaskSpec
Step 2

Grounder Tavily Nano

Searches the web for real sizes and masses. Nano pulls out the numbers and cites the page.

→ GroundedFacts + sources
Step 3

Builder Super

Places the objects and writes the motion plan: move, close gripper, lift, open.

→ Build (objects + actions)
Step 4

Runner our code

Runs MuJoCo with the Franka Panda, records video, and checks each goal with fixed tolerances.

→ RunResult (pass/fail, events, video)
Step 5 · on failure

Critic Super VL

Looks at 8 frames of the video plus the measurements and explains why it failed.

→ Critique (evidence, cause, fix)
Step 6 · on failure

Repair Super → Ultra

Rewrites the scene and plan using the critique. The first repair uses Super; later ones escalate to Ultra.

→ new Build, back to step 4
Loop Steps 4 to 6 repeat up to 4 attempts in total. Attempt 1 is built by Super, the first repair is Super, the second and third repairs use Ultra. Every call is traced in LangSmith with its latency, tokens and cost.
The product

The web app: every attempt replays in 3D

Seven recorded runs ship with the app (app/featured/), including fruit sorting and a mixed stack-and-sort, and replay instantly at no cost. Judges see a working example even if a model API is slow that day.

Decision log

Why it is built this way

Click a decision to see the reasoning and the alternative we turned down. New decisions are added at the bottom as the project moves.

D01The model never writes robot XML or codesafety · reliability
Decision
The robot comes from MuJoCo Menagerie, a library of hand-checked robot models. The Builder only returns object records (shape, size, mass, position) and a list of actions. Our code turns those into MuJoCo bodies with MjSpec.
Why
Model-written robot XML breaks in subtle ways (joint limits, inertia, mesh paths). Running model-written Python is a security risk. Data checked against a schema either passes validation or produces a clear error the model can fix.
Rejected
Letting the model write the MJCF objects fragment directly, as first planned. Generating it from validated data is just as flexible and cannot produce broken XML.
D02Pass or fail is decided in code, never by the vision modeltrust
Decision
Each goal is checked numerically. For on(A, B): A's bottom must be within 1.5 cm of B's top, A's center within half of B's width of B's center, and the gripper must have let go.
Why
Vision models can be confidently wrong. Code gives a repeatable answer, and it lets us run a batch evaluation with a real success rate. The Critic only explains a failure that code has already confirmed.
D03Motion targets are relative to objects, resolved when the step runscontroller
Decision
An action can say “move to the blue cube's center plus 5.3 cm up” instead of a fixed world coordinate. The position is read from the simulation at the moment that step starts.
Why
Objects settle and shift slightly. Relative targets keep the plan correct anyway, and they are much easier for a model to get right than raw coordinates.
D04Our own small IK solver instead of the mink librarycontroller
Decision
About 30 lines of damped least squares inverse kinematics on the 7 arm joints, with the gripper always pointing down and a gentle pull toward a natural elbow pose.
Why
It worked on the first run, has no library version risk, and returns clear errors like “target unreachable (IK error 4.2 cm)” that the Critic can use.
Rejected
mink, as listed in the original plan. Still installed; not needed so far.
D05Grasp assist, with the real gripper width as a hard limitphysics · honesty
Decision
When the gripper closes within 2 cm of an object, an invisible weld holds the object to the hand until the gripper opens. The weld is refused if the object is wider than 7.8 cm across the fingers, because the Panda gripper only opens to 8 cm.
Why
Pure physical grasping in simulation is fiddly and would make demos flaky. The width limit keeps it realistic: a real coffee mug cannot be picked up, which makes the Tavily sizes matter.
Disclosure
This will be stated plainly in the README, as planned from day one.
D06Schema-constrained JSON output, validated and retried oncemodels
Decision
Every model call uses Token Factory's json_schema response format, generated from our Pydantic classes. If the reply still fails validation, the error goes back to the model once.
Why
Tested both modes. With the schema, Super returned valid output on the first call. Plain JSON mode returned {"": ""}.
D07The Critic sees one grid image with reasoning switched offmodels · speed
Decision
The Critic gets one contact sheet of 8 frames instead of 8 separate images, and runs with Nemotron's reasoning disabled.
Why
With reasoning on, Super VL took 20 to 35 seconds and twice used all 4,000 tokens thinking, returning nothing. With reasoning off it answers in about 3 seconds. In 5 test runs, diagnosis quality was the same.
D08The Critic must write its evidence before its diagnosismodels · quality
Decision
The Critique schema starts with an evidence field. The prompt says sim events are ground truth, and the plan is shown as numbered steps.
Why
At first the Critic blamed the grasp in about half the runs, even though the log said the grasp worked. Two things fixed it: making the model quote the measurements first, and removing an example from the prompt that it kept copying. After the change, 5 of 5 runs were correct.
D09Demo prompts name real productsTavily
Decision
The Planner writes searches for concrete products (“Rubik's cube 3x3 dimensions mm weight”). Curated demo prompts use real objects such as a soda can or a tennis ball.
Why
A search for a generic “red cube” returned tungsten cubes and concrete blocks. Real products return published specs with a source link, which is what the Tavily prize looks for.
Guardrails
At most 3 searches per run, each cached on disk by query, so repeated runs cost nothing.
D10Escalate to Ultra only after a repair has already failedcost
Decision
Super builds attempt 1 and does the first repair. Only if that repair also fails does Ultra take over for the remaining attempts.
Why
Ultra costs about 3 times as much as Super per token. Most failures are simple (wrong height, wrong offset) and Super fixes them. Showing the escalation in the UI also demonstrates the cascade to judges.
D11Robot model fetched at a pinned version, not stored in gitrepo
Decision
scripts/fetch_menagerie.sh downloads only the Panda folder from Menagerie at one fixed commit. The Dockerfile will run the same script.
Why
The Panda meshes are 33 MB, and every one of them is needed. A pinned fetch keeps the repo small and the scene identical everywhere.
D12Spend is logged per call, with a hard stopbudget
Decision
Each model call appends its model, tokens and dollar cost to .cache/spend.jsonl. Calls are refused once dev spend passes $20.
Why
The Token Factory credit is $50 and has to cover the live demo through judging. A typical full run costs about $0.003.
D13GitHub repo stays private until submission dayprocess
Decision
Your call. Making it public is on the Friday checklist, because the rules require a public repo at submission.
D14The web app streams events, and every run is saved for replayproduct
Decision
The pipeline yields one small JSON event per step. The CLI prints them. The web server streams the same events to the browser with Server-Sent Events and writes them to runs/<id>/events.jsonl.
Why
One event format serves the CLI, the live UI and replays. Saved runs replay instantly and cost nothing, so the featured examples on the landing page always work. A run link (?run=…) can be shared.
Limits
At most 2 simulations at once; extra runs wait in a queue. Tested with 2 simultaneous runs.
D15Nano copies numbers; code does the unit mathsTavily · models
Decision
The Grounder asks Nano for the source quote first, then the size in millimetres and mass in grams, exactly as web pages write them. Our code converts to metres and kilograms, then checks the mass against the object's volume.
Why
With reasoning on, Nano took 20 to 25 seconds and still dropped the source links. With reasoning off it was fast but put millimetre numbers into metre fields. Copying is what it does well, so it now only copies (about 2 seconds) and code handles the arithmetic.
Example
A web page gave a soda can's empty weight (12 g). The density check sees 29 kg/m³, which is impossible for a full can. It replaces the value and labels it “mass corrected”.
D16If reasoning uses up the budget, retry once without itreliability
Decision
When a model returns nothing because its reasoning hit the token limit, the same call is retried once with reasoning off. The Builder's budget went from 8,000 to 16,000 tokens.
Why
One live run died because Super's repair spent all 8,000 tokens thinking. A demo must not end with an error for that reason.
D17Failures come from physics, not from stagingdemo honesty
Decision
The featured repair examples are real first attempts that failed on their own. The deliberately broken plan stays in scripts/try_repair.py as a test only.
Why
The tennis ball rolling off a cube is a real physics failure. The gripper's fingertips stop about 1.3 cm above an object's center because they reach the floor first. That leaves a small drop on release: harmless for a cube, enough to roll a ball. The Critic and repair have to deal with it, which makes the demo honest.
D18One CPU-only container; shadows off when rendering in softwaredeploy · speed
Decision
The web app and simulator ship as one Docker image with no GPU. MuJoCo renders through OSMesa (software OpenGL). In the container, shadows and floor reflections are off (SPEC2SIM_SHADOWS=0). On the Mac and on a GPU they stay on.
Why
Measured in the container: one frame took 183 ms with shadows and 38 ms without, at any resolution and shadow-map size. A 7 s clip went from 53 s to 12 s (16 s on 2 CPUs). A GPU endpoint would cost many times more for the same demo.
Trade-off
Live runs on the server look flatter than the recorded ones. The 4 featured runs keep their shadows.
Also found
The amd64 image can't be smoke-tested on an Apple-silicon Mac. MuJoCo's x86 build needs AVX instructions, which Docker's emulation lacks, so the process is killed instantly (exit 137). The same Dockerfile built natively for arm64 runs the full test scene.
D19Video frames go straight to diskmemory
Decision
Each frame is sent to the MP4 encoder as it is rendered. Only small thumbnails (10 per second, half size) stay in memory to build the Critic's grid.
Why
Multi-object tasks need up to 30 s of simulation. Keeping every full frame would take over 1 GB per run, and the server runs two at a time.
D20Goal types borrowed from NVIDIA's RoboLab, plus binsharder tasks
Decision
New goal types: inside (object in a bin), left_of, right_of, in_front_of, behind and upright. New object shape: bin, an open-top container (floor plus four walls) fixed in place. Up to 6 objects and 30 s per task.
Why
NVIDIA's RoboLab benchmark (built on Isaac Lab, RSS 2026) defines task success with the same kind of predicates: object_in_container, object_left_of and so on. Our inside uses RoboLab's test: the object's center must lie inside the container's cavity, measured in the container's own frame. Using the same vocabulary makes our tasks comparable to theirs and lets us show sorting and tidying, not just stacking.
Result
“Clear the table: put the red, green and blue blocks into the storage bin” passed on the first try for $0.007. Fruit sorting (apple and lime into a basket, soda can into a recycling bin) also passed first try. Sources: docs/research/07-nvidia-physical-ai.md.
D21Bins are scaled to tabletop size in code, not by the modelreliability
Decision
When the Grounder finds a real container bigger than the workspace allows, code shrinks it to at most 30 cm wide and 12 cm tall, keeps its proportions, and notes the original size. A bin's whole footprint, not just its center, must be inside the reachable area.
Why
The web gave real sizes: a 97 cm curbside recycling cart, a 38 cm basket. Walls that tall blocked the arm. Prompting the Builder to shrink them worked only sometimes, and two attempts were wasted on it. Then a bin centered at the edge of the workspace put its far half where the arm cannot reach.
D22Say “impossible” before spending money on repairshonesty · cost
Decision
After grounding, code checks every object that has to move against the gripper's 7.8 cm opening. If one is too wide, the run stops with a clear “physically infeasible” message before the Builder runs.
Why
One run grounded a real orange at 8 cm. The Critic correctly said no plan could ever grasp it. The loop still went on to escalate to Ultra, which then crashed. A robotics engineer would rather hear “your gripper is too small” in 10 seconds.
D23Guards against invented names and faked resultstrust
Decision
(1) The task spec is rejected unless every goal names a declared object and every inside goal points at a bin. The error goes back to the model for one retry. (2) If a placement goal already holds before the robot moves, the attempt fails with “objects must start away from their goal”.
Why
(1) The Planner once wrote a goal target of "target': ", a broken fragment of JSON. NVIDIA's Isaac Lab-Arena lists invented names as its top failure mode with Nemotron Ultra too. (2) A repair once tried to “solve” the fruit task by starting the orange inside the basket.
D24Recover JSON from Ultra, and fall back to Superreliability
Decision
If a reply has prose before the JSON, the last complete JSON object is used. If Ultra's repair is still unusable, the same repair is retried once with Super instead of ending the run.
Why
On its first live calls, Ultra sometimes wrote “We need to output JSON…” before the object, even with a strict output schema. That ended the run with an error.
D25Web sizes are checked against the model's own estimateTavily · trust
Decision
The Planner now writes its own rough size for every object. If a web size is more than 2× off that estimate, the web value is dropped, the estimate is used, and the UI says “web size … rejected”. For round objects, code fixes the dimension order (the diameter is the smaller sideways value).
Why
Once the gripper-width check (D22) existed, it caught bad grounding the Builder used to paper over silently. A “toy block” came back as a 44 × 10 × 21 cm product, and a soda can came back as [12.2, 6.6, 12.2] cm with diameter and height mixed up. Tavily is still the source when it agrees with common sense, which is most of the time.
D26The workspace is what the arm can actually reachcontroller
Decision
Objects and at goals must be at x 0.30–0.70 m and |y| ≤ 0.40 m, and within 0.78 m of the base. The limits are defined once and used by the Planner check, the Builder prompt and the scene check.
Why
A tower run failed all 4 attempts ($0.15) for two reasons. The Planner set the bottom block's goal to (0, 0), which is inside the robot's own base. And IK failed at x = 0.28 m, inside the old stated workspace. Solving IK on a grid of points showed where the gripper can really point straight down. The old limits (x from 0.25 m) were a guess.
D27Report every scene problem at oncecost · speed
Decision
Scene validation collects all problems (out of reach, too tall, overlapping, invented objects) into one message. The Builder may not add objects the task doesn't mention.
Why
One fruit-sorting run used all 4 attempts discovering one problem per attempt: a bin over the edge, then a bin too small, then an invented 1 m “table”, then that table's zero mass. With every problem listed, one repair can fix them all.
D28The browser draws the replay; the server only simulatesproduct · cost
Decision
Each attempt saves the position and rotation of every moving part, 30 times a second (about 0.5 MB for 30 s). The browser redraws the scene in 3D with three.js, using the robot's real meshes, which are exported once from MuJoCo and download as 1.4 MB. On the server, no MP4 is made. Only about 3 frames per second are rendered, for the Critic's image grid.
Why
Two weak points with one change. Cost: simulating the test scene on 2 CPUs went from 16 s to 2.9 s, so the smallest server is enough. Looks: shadows, a lab bench, the reachable area on the bench, and drag-to-orbit replace a flat software-rendered video.
Checked
The simulator is deterministic. Re-simulating the 9 attempts of the recorded runs from their saved plans reproduced every pass and fail exactly (scripts/add_viz.py), so the old runs got 3D replays with no model calls.
D29Export the scene, and show the checks in 3Dimpact · design
Decision
(1) An Export scene button downloads a zip: the objects as a MuJoCo XML file, task.json (real sizes with source links, plus the goals with their RoboLab names), plan.json, and a README with 4 lines of Python to load it next to the Menagerie Franka. (2) At the end of a replay, each goal appears as a ✓ or ✗ label on its object, with the measured error.
Why
Judges will ask where the AI is in the robot. The answer is that this is a tool for robotics teams: a sentence becomes a test scene with checkable goals, and the export makes that literal. The labels follow the Cosmos Cookoff winner's “see how it thinks” idea: the code's verdict is shown where it happened.
D30$5 a day cap on model spend for the public demobudget
Decision
Every model call is logged with a timestamp. Once today's spend (UTC) reaches DAILY_SPEND_LIMIT_USD (now $5), new runs are refused with a message pointing to the recorded runs, which replay for free. The $20 total cap for development stays. The app also starts without API keys, so replays work even if keys are missing.
Why
Judges can run tasks until Dec 15, and each run costs $0.005–0.15. You asked for $5 a day for now, to be lowered before judging.
D31Every success is stress-testedrigor
Decision
After a run succeeds, the final plan is re-simulated 16 times. Each time, every object starts up to 1.5 cm away, turned up to 9°, ±20% heavier or lighter and ±30% more or less slippery. Physics only, no model calls, a few seconds. The UI shows a robustness score.
Why
One success can be luck. This is a small version of Isaac Lab-Arena's sensitivity analysis. It separates good plans from lucky ones: the tennis-ball plan that failed on attempt 1 passes 11 of 20 variations, the repaired plan 20 of 20, and the "cube placed on the floor" plan 0 of 20. Knocking over a tower scored 14 of 16, which is honest nuance.
D32Drawers and knock-overs: tasks beyond pick-and-placeharder tasks
Decision
A new object type, drawer: a fixed cabinet with a drawer on a sliding joint and a handle bar. The gripper grabs the handle, and plans use exact anchors: D.handle, D.open, D.closed and D.slot (where to drop things in). New goals: opened, closed, inside a drawer, and toppled for knocking things over with the closed gripper.
Why
Opening a drawer is one of Isaac Lab's standard Franka tasks. Drawers and contact-rich pushing are also the examples the AnyTask paper uses beyond pick-and-place. "Put the tennis ball and the Rubik's cube into the drawer and close it" passed on the first try for $0.01: 16 actions across 3 goals.
Bugs found on the way
(1) The Builder prompt said yaw 0 closes the fingers along y; it's x. That had been wrong since day one and would have misled any grasp of a long object. (2) The Planner asked for a drawer to be both opened and closed at the end; goals now describe only the final state. (3) Two placement rules for cabinets left exactly one legal position, so the repairs went back and forth between them. The cabinet's back may now extend past the reach limit.
D33Realistic and plain views, and example tabsdesign
Decision
The 3D viewer has a Realistic / Plain switch. Realistic dresses the simple physics shapes by what they are: a soda can with a label and a metal top, a Rubik's cube with stickers, wood-grain blocks and drawer, a fuzzy tennis ball with its seam, an apple with a stem, a wicker basket. Textures are drawn in the browser, with no image files and no brand marks. The examples are grouped into tabs: Everyday objects, Basic shapes (plain view) and Beyond pick & place.
Why
You asked for both. Physics is unchanged: the README says the objects are primitives with real sizes.
D34Before / after, ghost, and fullscreendesign · video
Decision
A Before / after view shows the first failed attempt beside the final success. Both run on one clock and one camera, so dragging one turns both. A Ghost of failure switch draws the failed attempt's objects in red inside the successful replay. A fullscreen button covers both views.
Why
You wanted the failure and the fix visible on one screen for the video. Side by side, "the ball rolled 7.5 cm off" next to "✓ tennis_ball on rubiks_cube" makes the case without narration.
D35“Try to break it”product · trust
Decision
Move objects pauses the replay. You drag objects across the bench and press Re-run. The server re-simulates the same plan with the new starting spots (no model calls, a few seconds), and the result appears as a “Your test N” tab with its own ✓/✗ labels.
Why
It turns the stress test into something a judge can do with a mouse. It works because each plan step is relative to an object's current position (D03). In testing, moving the Rubik's cube 15 cm still succeeded.
D36One sentence → robot training data (LeRobot format)impact · NVIDIA fit
Decision
Generate training data re-runs a solved plan with random starting poses, masses and friction, keeps only the successful episodes, and saves them in LeRobot v2.1 layout. Each frame (10 per second) has the robot joint state, the commanded action, the object poses and a 320×240 camera image. Generation runs in the background with a progress bar.
Why
The Physical AI track names GR00T, and NVIDIA's GR00T pipeline trains on exactly this format. Isaac Lab Mimic and the GR00T synthetic-data blueprint also multiply demonstrations and keep the successful ones. Ours starts from a sentence instead of human teleoperation.
Checked
Loaded with Hugging Face lerobot 0.3.3. Its timestamp check caught frames 0.09 s apart instead of 0.1 s, which is fixed. Fruit sorting produced 20 of 20 successful episodes, 3,340 frames in 77 s.
D37Control-room look: dark theme, live cascade strip, hero autoplaydesign
Decision
Dark theme by default, with a switch. A strip of 7 nodes (Planner → Grounder → Builder → Simulator → Critic → Repair → Stress test) lights up as the run moves, each showing its model, time and cost, plus repeats (×2), escalation to Ultra, and the robustness score. The top of the page is tighter, so the 3D stage is visible on a laptop screen. The landing page plays a recorded run immediately.
Why
“The model cascade is a feature, show it” (project brief). Judges see the whole pipeline at a glance before reading any card.
Bugs and surprises found

Things that would have hurt later

fixed.gitignore

Comments at the end of a line broke the rules, so runs/ and .cache/ were never ignored. Videos and cached API results could have been committed.

fixedMesh paths

Including the Panda XML from another file made MuJoCo look for meshes in the wrong folder. Loading the scene with MjSpec and attaching objects to it solved it.

fixedEmpty Critic replies

The vision model spent its whole token budget on hidden reasoning. Fixed by turning reasoning off for that step (see D07).

fixedEmpty soda can

The Grounder gave a soda can 14 g, the weight of an empty can. It is now told to assume objects are in their everyday state.

fixedLangSmith “invalid token”

A false alarm: my check script never loaded .env. The key worked all along, and traces were arriving.

fixedDeadline day

The brief said Thursday Oct 30. Oct 30, 2026 is a Friday, which you confirmed. Both docs are corrected.

fixedRepair died mid-run

Super spent its whole token budget reasoning and returned nothing, which ended the run with an error. It now retries without reasoning (D16).

fixedContradictory goals

The Planner sometimes asked for a ball to be both “lifted” and “on the cube”. It now uses “lifted” only when the task ends with the object in the air.

fixedFalse “collision” hint

Normal arm lag of 2 cm was reported as a possible collision, which could mislead the Critic. The threshold is now 3.5 cm.

fixedAn apple is not an iPhone

Searching “apple dimensions” returned Apple product pages, so the apple got iPhone numbers and the orange got AirPods specs (1.6 cm). Queries now name the kind of thing (“apple fruit”), and Nano ignores results about a different kind of object.

fixedRound objects measured as boxes

Grasp width was measured with a box formula, so a rolled 6.8 cm tennis ball counted as 11.4 cm and was refused. Spheres and cylinders now use their real shape.

fixedCubes “tipped over”

A cube that rolled onto another face was reported as tipped 90°, even though it still sat flat. That would mislead the Critic. A box now counts as tipped only when no face points up.

fixed“Toppled” measured the wrong drop

Your prompt “stack three cubes in the drawer, then knock them over” exposed it: toppled compared against where an object started, so a cube that was stacked and then knocked down didn't count, and a cube that rolled onto another face did. It now uses the highest point the object rested at. The task itself is still too hard: the open part of the drawer is about 12 cm wide and the hand about 20 cm.

fixedFingers closed the other way

The Builder was told that yaw 0 closes the fingers along y. A drawer-handle grasp failed with "10 cm wide across the fingers", which exposed it: they close along x. Harmless for cubes and balls, so it went unnoticed for a day.

fixedTwo rules, one legal spot

"Keep the cabinet in reach" and "leave room to pull the drawer 12 cm" allowed only x = 0.59 m, so the repairs went back and forth between the two errors for 4 attempts. Only the front of the cabinet needs to be reachable.

fixed.env broke a script

.env sets MUJOCO_GL=egl, which is invalid on a Mac. It only crashed scripts that imported MuJoCo before the scene module corrected it. The setting now lives in the package's start-up code, which always runs first.

fixedMy own budget bug

While adding the daily cap, a text replacement made the budget check call itself forever, so starting any run crashed. A live test through the web API caught it before it shipped. There is now a unit test for the cap.

fixedSame prompt, different luck

The fruit-sorting prompt passed on the first try once, then failed all 4 attempts on the next run (oversized bin, then a bin at the edge of reach). The cause was moved from prompts into code (D21). This is why the batch eval exists.

Open risks

Not proven yet

resolvedNatural repair demo

Found two: the tennis ball rolling off the Rubik's cube, and a cube set down on the floor. Both are recorded in the app. Live runs vary: the tennis ball failed in 2 of 3 runs.

openCrash with 4 parallel CLI runs

One CLI run died during rendering while 4 ran at once in separate processes. Two at once in the web server works. The server's limit of 2 stays until this is understood.

resolvedUltra never called

Ultra has now run live several times: 15–96 s and $0.02–0.09 per repair. Once it wrote prose before its JSON, which is now handled (D24).

resolvedLinux rendering

The Docker image renders correctly with OSMesa on Linux (tested natively on arm64). It was 4× too slow until shadows were turned off (D18).

blockedNebius won't create resources

Creating a container registry or endpoint fails with “PermissionDenied”, even as a dry run, while reading the account works. AI Cloud billing is most likely not activated (Token Factory credit is separate). The commands are ready in deploy/nebius/README.md.

decidedDo we need GPUs?

No. The GPU was for server-side video rendering, which the browser 3D replay replaced. A GPU would only pay off for thousands of parallel stress-test runs (MuJoCo Warp / NVIDIA Newton), a self-hosted Cosmos Reason critic, or training policies. Glossary

Terms used in this project

MuJoCo
The physics simulator. Steps the world every 2 ms.
Menagerie
DeepMind's collection of ready-made robot models for MuJoCo.
MJCF
MuJoCo's XML format for describing a scene.
MjSpec
MuJoCo's Python API for building a scene in code instead of writing XML.
TCP
Tool center point: the spot between the fingertips that the controller moves.
IK
Inverse kinematics: working out joint angles that put the TCP at a target.
Weld
A MuJoCo constraint that locks two bodies together. Used for grasp assist.
Contact sheet
One image holding 8 timestamped frames of a run, sent to the Critic.
Token Factory
Nebius's API for hosted open models, compatible with OpenAI's client.
LangSmith
Tracing service. Shows every model call of a run as a tree.
OSMesa
Software OpenGL. Lets MuJoCo render video on a server with no GPU.
RoboLab
NVIDIA's Isaac Lab benchmark of 120 tabletop tasks. Its success tests inspired our goal types.
Isaac Lab-Arena
NVIDIA's framework for evaluating robot policies. It can generate environment specs from language.
Bin
Our open-top container: a floor plate and four walls, fixed in place.
Source: docs/explainer/index.html in the spec-to-sim repo. Updated as the build progresses.
