Spec-to-Sim

You type a robot task in plain English. A chain of NVIDIA Nemotron models turns it into a MuJoCo simulation, runs it, watches the video, and repairs the plan until the task succeeds. This page explains how it works, what has been built, and why each decision was made.

How it works

Six steps, and only the first three always run

Each step has one job and hands a validated data structure to the next. The models only ever produce data (JSON checked against a schema). Our own code builds the scene, moves the robot, and decides pass or fail.

Step 1

Planner Super

Reads the English task. Lists the objects, writes the success goals, and proposes web searches.

→ TaskSpec
Step 2

Grounder Tavily Nano

Searches the web for real sizes and masses. Nano pulls out the numbers and cites the page.

→ GroundedFacts + sources
Step 3

Builder Super

Places the objects and writes the motion plan: move, close gripper, lift, open.

→ Build (objects + actions)
Step 4

Runner our code

Runs MuJoCo with the Franka Panda, records video, and checks each goal with fixed tolerances.

→ RunResult (pass/fail, events, video)
Step 5 · on failure

Critic Super VL

Looks at 8 frames of the video plus the measurements and explains why it failed.

→ Critique (evidence, cause, fix)
Step 6 · on failure

Repair Super → Ultra

Rewrites the scene and plan using the critique. The first repair uses Super; later ones escalate to Ultra.

→ new Build, back to step 4
Loop Steps 4 to 6 repeat up to 4 attempts in total. Attempt 1 is built by Super, the first repair is Super, the second and third repairs use Ultra. Every call is traced in LangSmith with its latency, tokens and cost.

Decision log

Why it is built this way

Click a decision to see the reasoning and the alternative we turned down. New decisions are added at the bottom as the project moves.

D01The model never writes robot XML or codesafety · reliability
Decision
The robot comes from MuJoCo Menagerie, a library of hand-checked robot models. The Builder only returns object records (shape, size, mass, position) and a list of actions. Our code turns those into MuJoCo bodies with MjSpec.
Why
Model-written robot XML breaks in subtle ways (joint limits, inertia, mesh paths). Running model-written Python is a security risk. Data checked against a schema either passes validation or produces a clear error the model can fix.
Rejected
Letting the model write the MJCF objects fragment directly, as first planned. Generating it from validated data is just as flexible and cannot produce broken XML.
D02Pass or fail is decided in code, never by the vision modeltrust
Decision
Each goal is checked numerically. For on(A, B): A's bottom must be within 1.5 cm of B's top, A's center within half of B's width of B's center, and the gripper must have let go.
Why
Vision models can be confidently wrong. Code gives a repeatable answer, and it lets us run a batch evaluation with a real success rate. The Critic only explains a failure that code has already confirmed.
D03Motion targets are relative to objects, resolved when the step runscontroller
Decision
An action can say “move to the blue cube's center plus 5.3 cm up” instead of a fixed world coordinate. The position is read from the simulation at the moment that step starts.
Why
Objects settle and shift slightly. Relative targets keep the plan correct anyway, and they are much easier for a model to get right than raw coordinates.
D04Our own small IK solver instead of the mink librarycontroller
Decision
About 30 lines of damped least squares inverse kinematics on the 7 arm joints, with the gripper always pointing down and a gentle pull toward a natural elbow pose.
Why
It worked on the first run, has no library version risk, and returns clear errors like “target unreachable (IK error 4.2 cm)” that the Critic can use.
Rejected
mink, as listed in the original plan. Still installed; not needed so far.
D05Grasp assist, with the real gripper width as a hard limitphysics · honesty
Decision
When the gripper closes within 2 cm of an object, an invisible weld holds the object to the hand until the gripper opens. The weld is refused if the object is wider than 7.8 cm across the fingers, because the Panda gripper only opens to 8 cm.
Why
Pure physical grasping in simulation is fiddly and would make demos flaky. The width limit keeps it realistic: a real coffee mug cannot be picked up, which makes the Tavily sizes matter.
Disclosure
This will be stated plainly in the README, as planned from day one.
D06Schema-constrained JSON output, validated and retried oncemodels
Decision
Every model call uses Token Factory's json_schema response format, generated from our Pydantic classes. If the reply still fails validation, the error goes back to the model once.
Why
Tested both modes. With the schema, Super returned valid output on the first call. Plain JSON mode returned {"": ""}.
D07The Critic sees one grid image with reasoning switched offmodels · speed
Decision
The Critic gets one contact sheet of 8 frames instead of 8 separate images, and runs with Nemotron's reasoning disabled.
Why
With reasoning on, Super VL took 20 to 35 seconds and twice used all 4,000 tokens thinking, returning nothing. With reasoning off it answers in about 3 seconds. In 5 test runs, diagnosis quality was the same.
D08The Critic must write its evidence before its diagnosismodels · quality
Decision
The Critique schema starts with an evidence field. The prompt says sim events are ground truth, and the plan is shown as numbered steps.
Why
At first the Critic blamed the grasp in about half the runs, even though the log said the grasp worked. Two things fixed it: making the model quote the measurements first, and removing an example from the prompt that it kept copying. After the change, 5 of 5 runs were correct.
D09Demo prompts name real productsTavily
Decision
The Planner writes searches for concrete products (“Rubik's cube 3x3 dimensions mm weight”). Curated demo prompts use real objects such as a soda can or a tennis ball.
Why
A search for a generic “red cube” returned tungsten cubes and concrete blocks. Real products return published specs with a source link, which is what the Tavily prize looks for.
Guardrails
At most 3 searches per run, each cached on disk by query, so repeated runs cost nothing.
D10Escalate to Ultra only after a repair has already failedcost
Decision
Super builds attempt 1 and does the first repair. Only if that repair also fails does Ultra take over for the remaining attempts.
Why
Ultra costs about 3 times as much as Super per token. Most failures are simple (wrong height, wrong offset) and Super fixes them. Showing the escalation in the UI also demonstrates the cascade to judges.
D11Robot model fetched at a pinned version, not stored in gitrepo
Decision
scripts/fetch_menagerie.sh downloads only the Panda folder from Menagerie at one fixed commit. The Dockerfile will run the same script.
Why
The Panda meshes are 33 MB, and every one of them is needed. A pinned fetch keeps the repo small and the scene identical everywhere.
D12Spend is logged per call, with a hard stopbudget
Decision
Each model call appends its model, tokens and dollar cost to .cache/spend.jsonl. Calls are refused once dev spend passes $20.
Why
The Token Factory credit is $50 and has to cover the live demo through judging. A typical full run costs about $0.003.
D13GitHub repo stays private until submission dayprocess
Decision
Your call. Making it public is on the Friday checklist, because the rules require a public repo at submission.
Bugs and surprises found

Things that would have hurt later

fixed.gitignore

Comments at the end of a line broke the rules, so runs/ and .cache/ were never ignored. Videos and cached API results could have been committed.

fixedMesh paths

Including the Panda XML from another file made MuJoCo look for meshes in the wrong folder. Loading the scene with MjSpec and attaching objects to it solved it.

fixedEmpty Critic replies

The vision model spent its whole token budget on hidden reasoning. Fixed by turning reasoning off for that step (see D07).

fixedEmpty soda can

The Grounder gave a soda can 14 g, the weight of an empty can. It is now told to assume objects are in their everyday state.

fixedLangSmith “invalid token”

A false alarm: my check script never loaded .env. The key worked all along, and traces were arriving.

fixedDeadline day

The brief said Thursday Oct 30. Oct 30, 2026 is a Friday, which you confirmed. Both docs are corrected.

Open risks

Not proven yet

openNo natural repair demo

Real prompts pass on the first try because the Builder follows a reliable pick-and-place pattern. The demo needs one curated task that genuinely fails once and gets repaired.

openUltra never called

The escalation path is written but has not run live. Testing it costs about $0.01.

openLinux rendering

On the Mac, rendering uses CGL. The Nebius container will use EGL or OSMesa, which is untested until deployment tonight.

openVision model latency

Fast with reasoning off (about 3 s), but the first call of a session once took 35 s. A slow first call needs a waiting state in the UI.

Glossary

Terms used in this project

MuJoCo
The physics simulator. Steps the world every 2 ms.
Menagerie
DeepMind's collection of ready-made robot models for MuJoCo.
MJCF
MuJoCo's XML format for describing a scene.
MjSpec
MuJoCo's Python API for building a scene in code instead of writing XML.
TCP
Tool center point: the spot between the fingertips that the controller moves.
IK
Inverse kinematics: working out joint angles that put the TCP at a target.
Weld
A MuJoCo constraint that locks two bodies together. Used for grasp assist.
Contact sheet
One image holding 8 timestamped frames of a run, sent to the Critic.
Token Factory
Nebius's API for hosted open models, compatible with OpenAI's client.
LangSmith
Tracing service. Shows every model call of a run as a tree.
Source: docs/explainer/index.html in the spec-to-sim repo. Updated as the build progresses.
